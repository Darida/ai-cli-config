# TypeScript Web Architecture

A pattern for a small, framework-free TypeScript web client (Vite +
vanilla DOM, no React/Vue/etc.) talking to a Connect-protocol backend.
Apply this shape to a new TypeScript web client unless the project's
own README already documents a different, deliberate convention —
don't impose this over an existing, working pattern.

Several ideas here are deliberately translated from
`go-service-architecture.md`'s spirit (small single-responsibility
files, no accumulation files, domain-free shared code kept separate
from domain code) — but the mechanics differ a lot, because a browser
client has different constraints than an independently-deployed
service fleet: one bundle, one real dependency (the backend), and a
DOM to render into. Don't port `go-service-architecture.md`'s
`interface.go`/`impl/`/`module/` split, its `repository/` layer, or its
per-package error sentinels here — those exist specifically because
each Go service is independently deployed and independently tested
with swappable backing stores. None of that is true of a client
bundle, so building the same DI/mocking machinery for it would be
solving a problem this kind of project doesn't have.

---

## Highlights

- **Components are organized by real-world/visual identity, never by
  where they're used and never by backend wire shape.** See
  **components/** below for the concrete test.
- **No manually-generated wire client.** Message types and a typed RPC
  client are generated by `protoc` directly from the same `.proto`
  files the backend already owns — never hand-mirrored. See **Generated
  Client** below.
- **No hand-maintained "which views does this mutation affect" list,
  anywhere.** A single interceptor detects mutating calls generically
  (via the backend's own `request_id` convention) and triggers one
  global refresh after every one of them. See **Mutation Detection**
  below — this is what removes the need for a dedicated
  orchestration/`actions/` layer entirely.
- **No shared client-state singleton.** There's no `state.ts` and no
  app-wide cache — every component/view that displays backend data
  fetches it itself, every time it renders. See **No Shared State**
  below.
- **Whoever directly renders an interactive element owns wiring its
  behavior**, no matter how deep it is — a component with its own
  button wires that button itself; nothing "reaches down" from a
  parent to attach behavior to a child it didn't render. See **Event
  Wiring** below.
- **CSS is co-located per file**, using the bundler's built-in CSS
  Modules support — no new dependency, no global class-name collisions
  as the component count grows.
- **`framework/` is the one deliberate shared-code exception** — same
  reasoning as the Go doc: only genuinely domain-free infrastructure
  (an interceptor, a generic error-guard) is allowed to be imported by
  everything else.

## Folder Structure

```
src/
  main.ts              # boot only: build the transport/interceptors, create
                        # the refresh event bus, mount the root view, start
                        # the refresh-poll interval. No rendering logic, no
                        # RPC calls of its own, and no client-state
                        # knowledge — see **Mutation Detection** below.
  clients/
    <name>/client.ts    # a factory that builds a generated-client instance
                         # for a given service descriptor, using a caller-
                         # supplied backend URL and the framework
                         # interceptors — see **Generated Client** below
                         # for why this is a factory, not a singleton.
                         # Nested under a service name for when a second
                         # backend is ever added; exact shape still
                         # provisional.
  framework/
    event-bus.ts            # generic pub/sub — `subscribe`/`emit`, no
                             # knowledge of payload meaning or who's
                             # listening. See **Mutation Detection**.
    guarded.ts             # generic try/catch + caller-supplied error
                            # handler — knows nothing about creatures,
                            # nests, or any other domain concept.
    debug-interceptor.ts    # sets the shared dev-token header, unwraps a
                             # debug-chain response header into a thrown
                             # error — mirrors the backend's own
                             # framework/debugtrace, same shared-secret
                             # idiom, client side.
    refresh-on-mutation-interceptor.ts   # see **Mutation Detection**.
  components/
    <domain>/
      <name>.ts             # a UI piece + its own event wiring; owns and
                             # fetches whatever data it displays — see
                             # **No Shared State** below.
      <name>.module.css      # co-located, scoped styles — see **CSS**.
  views/
    <screen-name>.ts        # one file per screen/tab — assembles
                             # components, fetches whatever data the
                             # screen itself needs, nothing else.
    <screen-name>.module.css
  gen/                  # protoc output — regenerated and committed by
                         # the pre-commit/pre-push git hooks (mirrors
                         # backend/gen/'s own go-generate pattern), never
                         # hand-edited, never generated at build time —
                         # keeps `protoc` off the Docker build entirely.
proto/                  # synced copy of the backend's .proto — unchanged
                         # from before this pattern.
```

## components/ — Domain Identity, Not Usage Site, Not Wire Shape

**The test for where a component's folder lives:** would it still
belong there if the data behind it came from a completely different
API call, or was hand-typed for a mockup? If the answer depends on
today's backend response shape, the folder is wrong.

Two concrete mistakes this rules out, both made and corrected while
this convention was worked out:

- **Don't organize by which screen renders it.** A creature card isn't
  filed under whichever view happens to show it first — a different
  view might reuse it later, and nothing about the card's own identity
  changed. Organizing by call site also means a change to the backend
  API can force files to move between folders, which is exactly the
  kind of churn this rule exists to prevent.
- **Don't organize by which message a field is nested under on the
  wire.** A currency chip (🪙/💎 + amount) is a *currency* concept —
  reusable anywhere an amount needs a coin/gem icon next to it — even
  though today it only ever renders `PlayerState.coins`. Filing it
  under `player/` because that's where the field currently lives on
  the wire couples a UI folder to a backend implementation detail; if
  the backend later split balance into its own message (or a BFF/
  composition service merges two services' data the way this project's
  own read-composition layer already does for other fields), the
  component shouldn't need to move, because its real identity never
  changed.

The right question is "what would someone looking at the screen call
this," never "which proto message produced this value."

## views/ — One File Per Screen

A view assembles components and fetches whatever data it needs to
decide what to render (see **No Shared State** below). It does not own
business logic, does not call the generated client directly for
anything a component beneath it could own instead, and — per **Event
Wiring** below — only wires behavior for elements it renders *directly
itself*, not for anything a child component already owns.

## No Shared State — Every Component Fetches What It Displays

There is no `state.ts`, no app-wide cache, no singleton object holding
"the current player" or "the current creature list." Each
component/view that renders backend-derived data fetches it itself,
every time it renders — including two components that happen to show
the same underlying data today (e.g. both `views/collection-view.ts`
and `views/lab-view.ts` independently call
`RenderService.ListCreaturesView`, rather than sharing one fetch). This
is a deliberate simplicity trade against a small amount of duplicated
network traffic — acceptable per **Mutation Detection**'s "extra reads
are cheap" reasoning, since this is a debug console, not a
latency-sensitive product. An earlier draft of this pattern used a
`state.ts` singleton (a legitimate default for a stateful browser
client); it was rejected specifically to keep every component provably
self-contained, even at the cost of some duplicated fetches.

Three narrow, deliberate exceptions, each following the same rule as
**components/**'s own domain-identity test — a component that is
itself the sole owner/renderer of a piece of data may expose read
access to it, the same way `components/creature/creature-card.ts`
exports `shortName` for `components/nest/nest-card.ts` to reuse:

- **Connection config** (`backendUrl`, `playerId`) is owned by
  `components/debug-panel/connection-controls.ts` — the only place
  either is ever edited, persisted to `localStorage`. It exports
  `getBackendUrl()` / `getPlayerId()` / `getPlayerName()`; anything
  needing to call the generated client or format a resource name
  imports these rather than re-deriving connection state itself.
- **The activity log** is owned by
  `components/debug-panel/activity-log.ts`, which holds the log
  entries as local module state and exports `logInfo()` / `logError()`
  — any component that performs an action calls these directly after
  it succeeds/fails, the same way it calls the generated client
  directly (see **Mutation Detection**'s code sample).
- **Refresh signalling** (not app data — a pub/sub mechanism) still
  flows through the one `EventBus<void>` created in `main.ts` — see
  **Mutation Detection**. `views/game-view.ts` is the only thing that
  subscribes to it; every other component/view that shows live data
  gets refreshed because `game-view.ts` re-invokes its own render
  function, not because it independently subscribed to anything.

Everything else — a screen's own nav state (e.g. `game-view.ts`'s
"which building is currently open"), a fetched creature/nest list used
to build one screen — lives as an ordinary local variable inside the
file that uses it, and goes away when that file's render function
returns or is next called.

## CSS — Co-located, Scoped, No New Dependency

Every component/view's stylesheet sits next to the file it styles,
named `<name>.module.css`. The bundler's native CSS Modules support
(no plugin, no new package) scopes class names automatically — importing
one gives back a map of hashed class names instead of writing into the
global stylesheet. This is what keeps a growing component count from
colliding on class names the way one global stylesheet inevitably does.

Only genuinely cross-cutting things — CSS custom properties for the
theme palette, a `box-sizing` reset, `body` background — belong in one
small global stylesheet, imported once at boot. Same test as
`framework/` below: does this carry any domain/component-specific
knowledge? If yes, it doesn't belong in the global file.

## framework/ — The One Shared-Code Exception

Same reasoning as the Go backend's own `framework/`: code with zero
domain knowledge is safe to share broadly, because importing it can't
create a hidden coupling between two unrelated components' actual
logic — the thing keeping domain code un-shared everywhere else
protects against. Concretely:

- **`guarded(action, onError)`** — wraps an async action in try/catch
  and calls a caller-supplied error handler. Doesn't know what the
  action does or what "error" means to the caller; just runs it safely.
- **`debug-interceptor.ts`** — a Connect interceptor that sets a shared
  dev-token header on every outgoing request and, on failure, reads a
  debug-chain response header into a richer thrown error. This is
  infrastructure about *the wire protocol this backend speaks*, not
  about any one domain — mirrors the backend's own
  `framework/debugtrace` package on the other side of the wire.
- **`refresh-on-mutation-interceptor.ts`** — see next section. Doesn't
  know what a "creature" or "nest" is, only whether a request message
  happens to declare a `request_id` field.

Anything added later here needs to pass the same test the Go doc
applies to its own `framework/`: does it know anything about this
project's domain? If yes, it belongs under whichever
component/view/action actually owns that knowledge instead.

## Generated Client — `protoc` Directly, Not the Buf CLI

Message types and the RPC client are generated straight from the
backend's own `.proto` files (synced into `proto/`, same as before this
pattern) using one small `protoc` plugin — never hand-written, and
never hand-mirrored into a parallel `types.ts`. This was previously
hand-written specifically because no codegen toolchain existed in this
workspace; that's no longer the constraint, once the size problem below
is solved.

**Use plain `protoc` (already present on the machine via the
`protobuf-compiler` system package), not the Buf CLI.** They solve the
same problem, but at very different footprints — measured, not
assumed, when this decision was made:

| Package | Unpacked size |
|---|---|
| `@bufbuild/buf` + its platform binary | **126 MB** |
| `protoc` (system package) | already installed, effectively free |
| `@bufbuild/protoc-gen-es` (devDependency) | 55 KB |
| `@bufbuild/protobuf` (dependency, ships in bundle) | 1.79 MB |
| `@connectrpc/connect` (dependency, ships in bundle) | 858 KB |
| `@connectrpc/connect-web` (dependency, ships in bundle) | 67 KB |

Buf is a full toolchain (linting, breaking-change detection, a schema
registry client, its own bundled compiler) — far more than "run one
protoc plugin" needs. `protoc-gen-es` v2 is an ordinary `protoc`
plugin that, given `--es_opt=target=ts`, generates *both* message types
and a typed `GenService` client descriptor per proto `service` block —
confirmed by actually generating from `player_service.proto` and
inspecting the output, not assumed from docs. There's no second plugin:
`@connectrpc/protoc-gen-connect-es` exists but is the legacy v1
generator, peer-locked to `@connectrpc/connect@1.7.0` — installing it
alongside the v2 packages above fails with an unresolvable peer
conflict (`ERESOLVE`), and it isn't needed with v2 regardless. `protoc`
invokes the one plugin directly via `--plugin=`, no Buf module config
(`buf.yaml`/`buf.gen.yaml`) required. On disk-constrained environments,
this is the entire reason to prefer it — ~2.7 MB total versus 126 MB
for a CLI that does far more than this project needs from it.

**The generated client is built by a factory
(`clients/<name>/client.ts`), not a module-level singleton**, because
`createConnectTransport({ baseUrl })` bakes the backend URL in at
construction time — and this app's backend URL is a runtime-editable
text field, not a build-time constant. The factory takes `backendUrl`
as an explicit parameter rather than reaching for it itself, so this
file has no dependency on where that value lives; whoever calls it (a
view, a component) passes `connection-controls.ts`'s current
`getBackendUrl()` in, and rebuilds the transport fresh on each call so
editing that field takes effect immediately without a page reload.
This is cheap enough not to matter for a debug client; revisit only if
profiling ever shows otherwise.

## Mutation Detection — Why There's No `actions/` Layer

The backend already has a hard rule (`go-service-architecture.md`):
every mutating RPC's request message carries an explicit `request_id`
field; no read-only RPC does. That's not a convention worth
re-implementing on the client — it's a fact the client can *query*, via
the generated request's own schema, instead of a list a frontend
engineer has to hand-maintain and inevitably forgets to update when a
new mutating RPC ships:

```ts
const isMutating = "requestId" in req.method.input.field;
```

`refresh-on-mutation-interceptor.ts` checks exactly this, and — after
any call where it's true succeeds — emits on a generic `EventBus<void>`
(`framework/event-bus.ts`) rather than calling a refresh function
directly. The interceptor doesn't know what "refresh" means or who's
listening, only that a mutation happened; `views/game-view.ts` is the
sole subscriber (see **No Shared State** below) and re-renders itself
— its HUD and whichever building screen is currently open — in
response. The same bus is also what `main.ts`'s poll interval emits on,
so a periodic tick and an actual mutation are indistinguishable to the
subscriber — one `EventBus<void>` covers "something might have changed"
from either source. This is deliberately not surgical about *which* views are
affected by a given mutation: computing that requires
the frontend to model every possible backend side effect of every
mutation (a real, previously-hit failure mode — see e.g.
`DiscardCreature`'s `breeding_cancelled` response field, which exists
specifically because one such side effect had to be special-cased
after the fact). Refreshing broadly instead is correct by construction
and immune to a future backend change quietly going unnoticed on the
client. The extra reads this costs are cheap and don't matter for an
idle game or a debug console — this is not a tradeoff worth
re-litigating for a latency-sensitive product without re-measuring
first.

**This is why there's no dedicated orchestration/`actions/` layer in
the target architecture.** Once a mutating call needs no manual refresh
bookkeeping, and error-guarding is generic (`framework/guarded.ts`),
there's nothing domain-specific left to isolate into its own file — a
mutation collapses to "call the generated client, log a message,"
which is exactly two lines, entirely local to whichever component owns
the button that triggered it:

```ts
discardBtn.addEventListener("click", () => guarded(async () => {
  const resp = await client(CreatureService, getBackendUrl()).discardCreature({
    name: creature.name,
    requestId: crypto.randomUUID(),
  });
  logInfo(`Discarded ${creature.name}`);
}, logError));
```

## Event Wiring — Whoever Renders It Owns It

**Rule:** whichever function directly renders an interactive DOM
element wires that element's behavior — recursively, however deep. If
a view renders a button with nothing in between, the view wires it. If
a view renders a component and that component renders the button, the
component wires it, not the view.

This isn't in tension with "a component shouldn't know how it's used"
(see **components/** above) — it's the same underlying rule pointed at
a different question. "How I'm used" means *external context imposed
by a parent* — layout, spacing, "you're rendered next to a creature
card so take this margin" — a component should never need to know
that. Owning your own button's click behavior isn't external context;
it's the component's own complete, self-contained identity ("I am a
creature card; I have a discard button; clicking it discards me" is
true regardless of which view renders me). A component should be fully
self-sufficient about *what it is and does*, and fully ignorant of
*where it's placed*.
